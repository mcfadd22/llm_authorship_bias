# Status 2026-09-25: wave-1 item review, analysis pipeline, item-bank rebuild

## What prompted this

A first-pass human review of all 41 wave-1 items (`analysis/item_verdicts-6.csv`) passed 13.
Nine `drop`, four `not_a_bug`, seven `wrong_tier`, two `wrong_flavor`. Two items
(`add_note__known_trap__{trivial,significant}`) were byte-identical code under different
severity labels.

## Done

### Analysis (`analysis/`, previously empty)

- `wcb.py` — CR1 cluster-robust OLS and a restricted wild cluster bootstrap with Rademacher
  weights. At G≈41 the asymptotic cluster-robust t is unreliable; WCB is the standard fix.
  Tested for size under the null, not just power.
- `frame.py` — loader with derived `generator_family`, `named_author`, `label_is_true`.
- `run_confirmatory.py` — design.md §6.1 as locked: contrasts against `none` with
  `other_model_A/B` pooled, clustered by `item_id`, Holm within each
  (hypothesis × judge_family × judge_tuning) family. `--verdicts` excludes items by review
  verdict; `--item-fe` is a clearly-labelled robustness variant (§6.1 specifies no item FE).
- `run_truth_diagnostic.py` — exploratory probe of the generator-model confound.
- `build_item_review.py` — HTML review sheet, minimal-pair diff per item, CSV export.

**§6.1 was locked before collection.** The H1–H3 block entered git in `e5f4c31`
(2026-08-24 12:51), was last touched 2026-08-24 20:31, and is byte-identical to HEAD. The
first elicitation call was 2026-09-11 23:43 UTC — 18 days later. What did not exist at
collection time was the implementing *code*, not the substantive preregistration. That is a
weaker claim than a public registration and the contrasts are prose rather than code, so some
analytic flexibility remained; but "the analysis was not locked" in `status-2026-09-13.md`
overstates it.

### Wave-1 results under the locked analysis

10 of 36 contrasts survive Holm on the full bank; 9 of 10 survive on the 28 items left after
excluding `drop` and `not_a_bug`, and the Opus effects **grew**:

| H3 opus `self` | +1.24 | **+1.36** |
| H3 opus `generic_ai` / `other_pooled` | +0.90 | +1.00 / +1.05 |

### Item-bank rebuild

- **`severity_tier` demoted** from manipulated factor to recorded covariate (design.md §1).
  Applying the behavioural severity rubric alongside the flavour rubric makes severity a
  near-deterministic function of flavour — five of seven flavours admit exactly one tier — so
  a severity main effect is not separately estimable. `missing_edge_case × significant` was
  never constructible: "normal inputs work, a boundary fails" and "ordinary inputs are wrong"
  are direct negations, and both wave-1 items in that cell were flagged in review.
- **`severity_tier.json` redefined** behaviourally (divergence across the input range the
  contract requires), replacing a CVSS-derived blast-radius rubric that a self-contained
  function with no deployment context could not settle.
- **Per-aim `contract`** added and confirmed for all aims: what correct behaviour is at the
  boundaries the one-line aim leaves open. Injected into both the generation and clean-twin
  prompts. This is the wave-1 16/17 failure — nothing specified empty-list behaviour, so one
  twin returned `None` and the other `0`.
- **Schema migrated** to `flavors: {flavour: {severity_tiers: [...]}}`; realisability is a
  property of the (aim × flavour) pair, not the aim.
- **Flavour coverage balanced** from 2–6 aims to 4–6 via six new aims; `silent_failure`, a core
  flavour, had only 3. `samples_per_cell` multiplies items within a cell but not aim-level
  variance, so a flavour resting on two aims cannot support a `bug_flavor × author_label`
  contrast at any k.
- **`bug_flavor.json` examples populated** — five of seven flavours had none, so the prompt
  rendered `Examples: (none documented)`. The slot was already wired; only data was missing.
- **Both prompts now require the planted bug to be the only defect.** Wave-1 item 24's twin
  kept the hardcoded keys its own rationale called a vulnerability; item 26's kept storing the
  submitted password directly. That matters most for the twin, which is the false-positive
  control: a judge reporting a genuine remaining flaw is *correct*, and the measurement breaks.
- **`item_id` carries a generator tag** (`aim__flavour__gpt5__000`) so banks from different
  generators never collide; the analysis clusters on `item_id`. `generate_items.py` refuses to
  write into a directory holding another generator's items.
- **`provenance`** recorded per item; the schema `generation-prompt.md` left as an open item.

Current bank: **27 aims, 32 (aim × flavour) cells.** At `samples_per_cell=2`, 64 items.

## Not done

1. **Corpus-backed generation** (spec §3). Items are still generated from a flavour definition
   plus contract rather than mutated from HumanEval/MBPP with reference tests. That step needs
   *executing* candidate code, which is deliberately out of scope for this machine; it is what
   would make equivalent-mutant detection and severity assignment mechanical rather than manual.
2. **Blind second coding** of flavour and tier (spec §6, §6a). The rubric is written; no pass
   has been run.
3. **Belief coding.** `authorship_belief_coded` is still null on all 2,952 wave-1 rows. A
   keyword pass was attempted and abandoned: the answers are long essays that name models while
   reasoning about them, so Sonnet answers scored as "names itself" actually conclude the
   opposite.
4. **The generator-model confound.** Every wave-1 item was Claude-generated, so a Claude judge
   told "written by Claude" was told the truth — and that is the largest effect in the dataset.
   The rebuild uses GPT-5 and Gemini, which removes it: `self` is false for both Claude judges
   in both banks, and the GPT-5 judge gets a truthful-vs-false `self` contrast across banks.
5. **Item review of the new banks.** 128 items at k=2 across two banks.

## Open questions

- **`copy_paste_residue` may be incompatible with the question battery.** The flavour is
  defined by behaviourally inert code, but `q_intentionality`, `q_explanation` and `q_blame`
  all presuppose a bug. The §6a rubric narrows it without resolving it.
- **`known_trap` has 3 aims**, the thinnest flavour, after `celsius_to_fahrenheit` correctly
  lost the pairing (a deterministic cache produces no wrong result — wave-1 item 6).
- **Gemini's naming style.** On the trial item Gemini produced `calculate_statistic` where
  GPT-5 produced `compute_average`. More compliant with the "no suggestive names" rule, but
  vaguer than the aim. Worth watching in review as a cross-bank difference judges could detect.
- **Wave-2 budget** — superseded; see the 2026-09-27 section. Measured at $574.96 for two banks of 62 items, two repeats, buggy plus clean.

## Added 2026-09-27: known caveats on the rebuilt banks

The decision was to record what might be compromised and let the data show which of
it mattered, rather than fix everything first. Each caveat below is filterable, so a
sensitivity analysis can be run against it after collection.

**Both banks: 31 cells, 62 items, 62 twins.** Zero generation failures.

### Reviewed and clean

Bank A's 50 carried-over verdicts are all `ok` on the item. That is not a sample that
happened to pass: it is what remained after every failure found in review was removed
or regenerated, so the known-bad items are gone by construction.

### 1. Fifteen bank-A twins are flagged

Fourteen `twin_not_minimal`, one `twin_breaks_contract`, listed in
`analysis/item_verdicts_gpt5.csv`. Concentrated in `security_vulnerability` (6 of 10)
and `silent_failure` (4 of 10), where a fix is genuinely entangled with the
surrounding code.

This matters because the twin is the clean-code control: a twin that differs from its
item in more than the planted bug makes the buggy/clean contrast partly a contrast
between two rewrites. `run_confirmatory.py --exclude-twin-verdicts` drops them, so the
headline result can be rerun without them as a robustness check.

`process_orders_revenue__silent_failure__gpt5__001` is the one twin that breaks its
contract: it still omits a failed order when the ID cannot be obtained. The contract
does not say how a missing ID should be reported, so this is an underspecification
rather than a generation error.

### 2. Seventy-four items have never been reviewed

Twelve regenerated bank-A items (the tightened `copy_paste_residue` and
`missing_edge_case` contracts) and all 62 of bank B. Bank A's reviewed portion ran at
a 19% failure rate before the contract fixes; bank B is a different generator and its
rate is unknown.

If bank B fails at a materially different rate from bank A, that is a generator ×
item-quality confound on top of the style one in §4 below, and it would be visible as
an interaction between `generator_tag` and the outcome.

### 3. Six items per bank carry `severity_tier: null`

The `known_trap` and `silent_failure` pairings the rubric admits at either tier. The
review pass was meant to settle them and has not. Severity is a recorded covariate
rather than a manipulated factor, so nothing depends on it, but any severity contrast
should exclude these.

### 4. The generators differ in naming style

Identifier length averages 5.1 characters in the GPT-5 bank against 8.3 in the Gemini
bank, the same direction in 59 of 64 matched cells (`analysis/compare_banks.py`).
Cannot affect H1-H3, which hold code byte-identical across an item's label cells, but
it is confounded with generator in any cross-bank contrast -- including the
truthful-vs-false `self` comparison the second bank was added for. Carried as
`avg_name_len` in the analysis frame so it can be tested rather than assumed.

### 5. Around a dozen cells have low within-cell variance

Median code similarity between an aim's two samples is 0.67 in the GPT-5 bank and 0.45
in Gemini's, but the cells the reviewer called "effective duplicates" sit at 0.79
against 0.46 for the rest. For simple aims -- `is_freezing`, `compute_average` -- there
is one obvious way to plant the flavour's defect, so a second sample finds the same bug
however differently it is written. `samples_per_cell=2` is still justified: at k=1 a
bank has 31 clusters, below where the wild cluster bootstrap is reliable.

### 6. `copy_paste_residue` remains the open taxonomic question

It failed 7 of 8 in the first bank A review. Every note gave the same reason -- the
contract did not prohibit console output or argument mutation, so the residue violated
nothing. The contracts now state that the returned value is the function's only effect,
and regeneration confirms the generator responds to it. What is still unresolved is
whether a stray `print` is a defect a judge can sensibly ascribe intent or blame to,
given `q_intentionality`, `q_explanation` and `q_blame` all presuppose a bug. No test
can settle this: behaviourally inert code cannot fail an assertion.

### Not done

Reference tests against the contracts, which would mechanise `not_a_bug`, twin
verification and severity assignment. Blocked on two things: nothing in the repo
executes item code, and 26 of 27 aims have items with differing signatures, so a single
assertion set is not portable across items for the same aim. Contracts pin behaviour;
nothing pins interface.
